# 音质、稳定性与交互质量标准

阶段 0 · P0-T4 · 2026-11-26

发起人确认以下质量原则及工程目标，唯一明确修改是**连续播放长测为 4 小时**。工程数值可在 iPhone 17 真机测量后校准并说明原因。下列矩阵定义待执行的口径，无 Fidelune 实测数据。P1 建立证据与校准，G4 用正式候选版本验收。

## 1. 音源还原与验证证据

| 性质 | 验收口径 |
| --- | --- |
| 硬性 | 播放器默认忠于源规格。不主动重采样、降低有效位深或改变声道布局，不加 EQ、响度归一化、混响等非必要信号处理。优先可用最高质量，用户显式质量设置与受限链路须如实记录。 |
| 硬性 | 切歌、切路由、开始/停止和恢复时无应用造成的爆音、异常卡顿。兼容规格曲目的自动无缝过渡追加零间隙、不丢样；不同规格允许设备重配置的必要间隔，原生规格优先。 |
| 目标与限制 | 可行的无损有线路径以 Bit-perfect 为核心质标。有损源按解码结果准确输出，避免应用二次有损压缩。系统或设备协商造成的转换要区分于应用处理；蓝牙遵循系统协商。音源数据率、设备运行采样率、链路编码/码率和有效位深分开记录。 |
| 支持格式目标 | DSF、WAV、FLAC、ALAC 及常见有损。DSF 是 DSD，单独验证原生 DSD / DoP 与实际 DAC 模式。若只可解码后转 PCM，明示转换且不标原生/Bit-perfect DSD。最终可交付格式和降级行为由 G1/G2 据实测定。 |

### P1-T2 音频与路由用例

1. **基础 PCM 规格阶梯。** 用 16 bit / 44.1 kHz 和 24 bit / 48、88.2、96、176.4、192 kHz FLAC；有线 DX5 II 预期显示分别匹配对应采样率。加入 ALAC、WAV（包含 16/24 bit 和同采样率不同位深）、常见有损、DSF，以及已知内容的连续、短曲、静音边界和损坏/截断样本。先记录每个文件的来源、校验值、解析规格、时长和声道。扬声器必测，蓝牙借测后补；AirPlay 已延后。
2. **切换组合。** 相邻同规格与混规格（如 44.1 → 96 → 192 → 48 kHz，另测同采样率不同有效位深/声道）、同专辑混规格、混合歌单，分别测自动/手动/连续快速切歌、随机、暂停/恢复和跳转，覆盖热插拔及中断返回。mpv 优先验证默认 `weak`，仅将 `yes`、`no` 作必要对照，记录真实打包版本、滤镜链、是否重建输出与转换决策。细节和备选顺序见[技术调研](../research/TECH_STACK_COMPARISON.md#mpv-的重采样与-avaudiosession)。
3. **分层观测。** 在相同时间点记录源（编码、采样率、有效位深、声道）、引擎解码及输出（实际格式和应用滤镜/转换）、会话（所请求值、激活后实际值、当前路由、可获取的通道/缓冲信息）、硬件（DX5 II 显示或独立测量）。初始化、同/异规格切换、锁屏、中断、热插拔后各取证。证据级别分别为读取音源、观察应用层、观测系统会话、外部测量。每个字段标明来源、路由、不可获取原因和是否只为推断。音频链路展示必须区分音源与可读取的输出，蓝牙 codec、链路码率、物理有效位深等无证据时记为不可知。
4. **还原与无缝。** 用预知 PCM 样值的无损样本对比解码和应用输出，同步对齐后核对样值及声道，区分位宽封装和有效精度丢失。DAC 显示匹配只能支持采样率结论。若要声明端到端 Bit-perfect，需有适宜的数字采集或可靠校验手段核对实际样值，现有 DAC 显示不足时标记端到端未证实。用从同一连续测试信号切出的同规格文件核对边界是否插入额外静音、丢样或产生瞬态，并按可用设备保留轨迹、录音或受控试听证据与其局限。源文件本身的静音、编码延迟和系统重配分别记账。
5. **可区分失败原因。** 应用引入非必要转换、兼容规格额外间隙、切歌爆音等按缺陷处理。系统/设备拒绝目标规格时，记录实测链路限制及是否可在有线主路径满足要求。无外部数字证据时提交可验证的应用层结果与开放风险，请发起人在 G1 判定证据够不够，禁止把采样率一致宣传成整条链路 Bit-perfect。

Apple 的采样率 API 提供请求和会话实际规格查询，硬件/协议边界另测。Apple Music 的公开说明可作蓝牙和有线规格的背景，其结果不移用到 Fidelune。 [Apple 会话偏好](https://developer.apple.com/library/archive/qa/qa1631/_index.html) · [mpv 输出选项](https://mpv.io/manual/stable/#audio) · [Apple 无损音频说明](https://support.apple.com/en-us/118295)

## 2. 播放响应与操作反馈

以下数字是 iPhone 17 本地播放的**工程目标**，仅「兼容规格无缝零额外间隙」是硬性要求。建议按同一构建和音源重复采样，保留原始耗时与分位值，以及冷/暖启动、路线、格式与是否后台扫描的分组。可见反馈与实际音频延迟分别计时，底层尽快响应，状态与动效可并行。

| 指标 | 初始目标 | 从哪里计时 |
| --- | --- | --- |
| 点击的可见反馈 | ≤ 100 ms | 用户操作至首个可见状态/过渡反馈。 |
| 短交互动效 | 150～250 ms | 过渡自身时长，阶段 2 随界面细化。 |
| 首次本地起播 | ≤ 500 ms | 播放动作至第一段预期样值输出，样本避免前导静音。 |
| 同规格本地手动切歌 | ≤ 300 ms | 切歌动作至目标曲可听，自动无缝另测。 |
| 本地进度跳转 | ≤ 300 ms | 松手/提交定位至正确片段开始输出。 |
| 兼容规格自动过渡 | 0 额外间隙 | 用连续信号检查实际音频边界。 |

「质感」通过按钮即时反馈、简洁连贯的封面/曲目信息切换和进度条实时跟手呈现。快速切歌优先最新请求，取消或忽略过时请求与动效。自动无缝的音频衔接独立于 UI 动画，不通过延后音频制造动效节奏。100 ms 接近离散反馈可感知阈值；其他目标来自本次讨论，Apple Music 没有提供这些实测数值。 [Apple 响应性](https://developer.apple.com/documentation/xcode/improving-app-responsiveness) · [Apple 动效](https://developer.apple.com/design/human-interface-guidelines/motion) · [NN/g 响应时间](https://www.nngroup.com/articles/response-times-3-important-limits/)

## 3. 播放稳定性与系统控制

| 场景 | 硬性行为与证据 |
| --- | --- |
| 亮屏/锁屏与前后台切换 | 同一源、同一路由的音质与播放连续性保持。对照会话、音频输出和进度，锁屏不会造成卡顿或隐性降质。 |
| 锁屏/控制中心命令 | 播放、暂停、切歌和进度与应用内状态一致，核对显示信息和实际音频。 |
| 来电、闹钟等中断 | 参考 Apple Music，在系统中断开始/结束时正确更新状态；根据系统恢复提示及用户期间的操作决定是否续播，保留位置并避免重复起播。 |
| 耳机或 DAC 拔出、路由变更 | 停播或暂停以避免意外外放，验证路由变更后状态和可读规格。测试接回设备和输出切换。 |
| 损坏或不可读文件 | 自动跳过且后续正常曲目继续，录下跳过原因，防止连续坏文件或循环模式造成无休止重试。产品提示形式待定。 |
| **连续播放 4 小时** | 使用混合格式和采样率，执行多次锁屏、亮屏及前后台切换。验收无非预期中断、崩溃或持续内存增长；保留事件、轨道/路由切换和内存趋势，允许自动记录并抽检，无需连续人工试听。 |

通过系统背景音频能力、`AVAudioSession` 通知及 MediaPlayer 命令/正在播放信息整合。以实际耳机拔出、来电和闹钟为准，区分系统正常暂停与播放器故障。P1 覆盖会话/背景基本行为，完整长测及可用路由在正式候选重验。 [音频中断](https://developer.apple.com/documentation/avfaudio/responding-to-audio-session-interruptions) · [路由变更](https://developer.apple.com/documentation/avfaudio/responding-to-audio-route-changes) · [媒体命令](https://developer.apple.com/documentation/mediaplayer/mpremotecommandcenter)

## 4. 曲库处理、数据和检索

用千首量级快速诊断、**10,000 首标准曲库**、**50,000 首压力曲库**。固定样本清单，覆盖容器内及授权目录、各种文件大小、格式与分层目录、大图封面、分碟和同专多条目、标签缺失、中日文短词及全半角、外部不可访问与坏文件。采集首次无库、首次可浏览、完整处理、无变重扫、少量新增/变更/移除和播放并发；分开记录规模、缓存冷热、存储来源、变化数及失败/恢复次数。

| 指标 | 初始目标及口径 |
| --- | --- |
| 万首首次扫描 | ≤ 60 秒为建议值，受格式、封面、来源与目录结构影响，待实测校准。计起扫至索引可用且批次完成，另记第一批可浏览时间。 |
| 无变化重扫 | 无重复标签解析，文件状态与授权检查可继续。 |
| 增量扫描 | 解析工作量应随变化文件量增长，目录枚举/检查成本单独记录。有限并发后台解析及批量提交，已经解析的音乐可以浏览；中断后安全接续或重跑。 |
| 搜索、筛选、排序 | 各自首屏 ≤ 100 ms 的目标，计操作后可见首屏更新。大型结果分页/按需加载，忽略过时查询。分别测英文前缀、中日文一/两/多字、精确筛选及扫描并发。 |
| 播放优先 | 扫描、查询、大图解码不得造成可感知播放卡顿。允许降低并发或延长扫描时间。 |
| 数据完整性 · 硬性 | 撤权/移盘与重扫时保留组织成果和纠错结果，文件尽可能重新关联；搜索索引可重建。模拟中断、重扫、过期、清缓存、备份导出恢复与迁移。持久纠错标记、未过期恢复记录、收藏和其他组织数据应符合各自生命周期，原音频及标签保持原样。 |

采用成熟扫描流水线与 SQLite 查询/事务模式，先定位 I/O、解析、数据库或 UI 各自的耗时再调并发。 [Navidrome 扫描参考](https://www.navidrome.org/docs/usage/admin/cli/scan/) · [SQLite 查询规划](https://sqlite.org/queryplanner.html) · [SQLite FTS5](https://sqlite.org/fts5.html)

## 5. 界面流畅度、资源与能耗

| 项目 | 初始目标或验证口径 |
| --- | --- |
| 冷启动 | ≤ 1.5 秒至可操作，从结束进程后的启动动作计至主导航/页面接受输入，区别首次建库与已有曲库。 |
| 页面切换 | ≤ 100 ms 开始反馈。扫描、图片读取和后台任务不阻塞操作。 |
| 列表 | 适配当时设备刷新率，避免明显卡顿。120 Hz 场景帧预算约 8.3 ms；记录实际刷新率、UI/渲染帧时间、掉帧和长帧，不能把显示刷新率写作应用实际帧率。大封面按需、恰当尺寸解码。 |
| 体验对照 | 在同一 iPhone 用 Apple Music 做同类操作对照，参考运动连贯性、响应、反馈和位置保持。阶段 2 决定具体交互及视觉。 |
| 资源 | 核心体验优先，CPU、内存、耗电无当前绝对限额。记录屏亮/屏灭、播放/扫描、冷/热的峰值和趋势，以及缓存大小、清理与重新生成；优化息屏无效渲染、重复 I/O/解码、任务频率和并发，保持源音质。 |

用 Flutter profile/发布构建和原生测量对照，记录设备、系统/构建、锁屏、低电量和温度等条件，避免以 debug 代替交付体验。 [Flutter 性能分析](https://docs.flutter.dev/perf/ui-performance) · [Apple 帧预算](https://developer.apple.com/documentation/xcode/improving-app-responsiveness)
